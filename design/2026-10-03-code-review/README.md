# 代码整理与结构审阅（2026-10-03）

范围：原生微信小程序的页面、组件、计分引擎、存储、展示转换和 JavaScript 测试。以保留现有行为与历史记录格式为边界；没有变更麻将规则、页面布局或已有本地数据。

## 2026-10-04 存档迁移统一

本节更新此前“兼容尚未统一”的结论。已新增 `utils/game-migrations.js`，由 `utils/game-storage.js` 统一接入。

### 格式与入口

- 当前存档外层、每场历史记录、逐局记录增加 `schemaVersion: 1`。原有逐局 `version` 保留，二者职责不同；旧本场换算由 schemaVersion 防止重复执行。
- 所有页面的 currentGame/gameHistory 读取改用 `GameStorage.current()` / `history()`，新写入也生成统一格式。
- 旧格式的点数换算、红五位置恢复、役种名称补全、单家荣和输入恢复、缺失轮次和 ID 补全均集中在迁移模块。表单/展示工具保留调用入口，可用于单独恢复输入或直接展示旧记录，但不再自行实现旧格式判断。
- `ron-entry` 对已统一记录直接使用保存的卡片输入；纠错能力由 `correctionAvailable` 表示，缺少前后快照或输入时不开放纠错。

### 首次升级与失败保护

读取旧数据 → 在副本上转换及校验 → 写入原始备份 → 写入新版 → 返回新版。再次读取不改点数、不重新生成 ID、不重复写入。

备份键为 `currentGame.migration-backup` 和 `gameHistory.migration-backup`，保存相应数据集最近一次升级前的原始值。备份不是无限版本历史；后续再次遇到需要迁移的数据集时会更新。清空全部历史会同时清除历史迁移备份。

备份写入失败则不写主存档；主存档写入失败则保留原主存档及已写备份。损坏结构、不支持的未来 schemaVersion 会中止操作并提示，不以空存档替代。保存入口也检查现有存档，防止旧客户端覆盖未来版本。单次历史迁移按整个列表转换成功后再写入，避免半列表升级。

### 不可还原的信息

旧红五位置沿用原恢复策略并标记 `redPlacementInferred`，此标记随手牌再次保存；仅有名称的旧役种标记 `inferred`。缺失快照不生成虚假的快照。格式迁移不修改玩家点棒、最终成绩或对局规则；原有“继续对局采用自由记分”的政策仍独立保留，不混入格式转换。

### 验证

`node test/run.js`：19/19 套通过；新增迁移测试覆盖重复读取、备份顺序、失败后重试、未来版本、损坏批次、数字 ID、规则/点棒保持、缺失快照、推断标记和新写入无需再次升级。`git diff --check` 通过。实际设备存档将在小程序下次读取时升级，本次仅对测试模拟存储验证，未操作微信开发者工具中的真实数据。

一般计分提交的多键存储失败恢复仍是独立待办，本次完成的是迁移阶段的失败保护。

## 2026-10-04 实施结果

按“保留旧存档兼容、独立与内嵌入口、现有规则转换政策”的边界完成第二轮整理：

- 表单增加 `initializeInput / restoreInput / submitResult / dismissInput` 接口。独立页面接入真实导航及 EventChannel；内嵌组件直接传递配置、恢复数据和事件，不再伪造 EventChannel 或调用页面 onLoad。

- 新增 `utils/ron-entry.js`：荣和卡片统一推导单家赢家、点数、多家模式和可提交状态；编辑旧单家记录时统一恢复。旧扁平字段仍用于存档格式和旧调用边界，卡片存在时以卡片为准。打开多家中的某张卡片不再覆盖表单的赢家字段。
- 新增 `utils/round-transaction.js`：集中组装新增/替换记录、版本、ID、输入与前后快照；页面负责交互和提交。点数计算、记录准备均不依赖微信 API。
- 新增 `utils/yaku-records.js`：共享役种排序和旧名称补全；计分模块不再依赖 round-view 展示模块。
- 新增 `utils/report-actions.js`：独立结算页、历史结算组件共用复制与图片战报入口。移除记分板不再使用的结算弹窗状态及战报构建/分享方法。
- 清理历史页未使用的旧详情区样式；保留当前卡片和排名样式。
- 记分板由上一轮 849 行减至 734 行；相较最初 1061 行减少 327 行。缩减主要来自职责拆分，不代表总功能减少。

## 后续建议，按优先级排列

### 1. 继续拆分记分板的录入流程与纠错事务

位置：`pages/game/board.js` 的 `_commitRound`、`editLastRound`、`_navigateToCalc`、`_openInputOverlay`。

页面仍有 849 行。它同时持有单家/多家荣和表单、自摸表单、纠错快照、存储提交和多个弹层的状态。`selectedWinner`、`ronEntries`、`multiRonMode` 有相互推导关系，当前靠多处 `setData` 保持一致。

建议下一步先将表单状态转换独立成明确的输入/输出函数，再将纠错的版本、before/after 和输入快照组装抽成记录事务模块。页面只负责事件、展示和一次提交。不要简单把大量依赖 `this.data` 的方法分散到多个 mixin，隐式耦合仍会存在。

### 2. 收敛计算器的两种宿主适配

位置：`utils/embedded-entry.js`、`pages/calculator/definition.js`、`pages/quick-score/definition.js`、`components/*-entry/`。

当前已复用表单、样式和定义，优于复制两份表单；问题是组件反向引用页面，使用伪造的 EventChannel 驱动 `onLoad`。记分板还将配置拼成 URL，再由 `_openInputOverlay` 拆回对象，并保留导航返回相关状态。

建议共享表单逻辑接收结构化配置及 `restore / confirm / dismiss` 接口；独立页面和内嵌组件只提供宿主适配。完成迁移后再删除 URL 编解码和页面返回兼容分支。现有回归测试仍覆盖旧调用方式，本次没有直接删除这些路径。

### 3. 从自动保存中移出规则迁移

位置：`pages/game/board.js` 的 `_autoSave`、`_entryState`，以及 `utils/game-rules.js`。

`_autoSave` 除了保存，还会把进行中的对局 `gameType` 改成 `free`；`_entryState` 又对纠错前的规则做兼容转换。这让存储动作隐含改变对局规则。建议将“旧对局恢复成自由记分”的政策写成独立迁移函数，在加载时统一处理，并覆盖恢复、纠错、结算后的再次打开。

这是已有行为，本次保持不变。东风/半庄、飞人、延长等规则仍涉及旧记录和测试，不应仅因为新建对局采用自由模式就删掉。

### 4. 整理展示层依赖与样式归属

位置：`utils/round-view.js`、`utils/game-round.js`、`utils/battle-report.js`、`pages/game/history.wxss`、`pages/game/board.wxss`。

- 役种排序与旧版名称补全目前在 `round-view` 中，计分记录也调用它。后续可提取独立的役种元数据/记录规范化工具，避免领域模块依赖展示模块。
- 结算组件已复用页面模板和样式，但分享行为还有两份相近实现；适合随着宿主适配一并收敛。
- 历史页仍有 `.card-detail`、`.detail-section`、`.round-item` 等旧详情区样式；记分板有 840 行样式。建议按实际 WXML、include/import 链和动态 class 核实后删除，并在微信开发者工具验证弹层与长列表。仅搜索一次类名不足以证明所有样式都无效。

## 建议保留

- `tiles → decompose → yaku/fu → score` 已有合理的计算职责边界，`yaku.js` 较长主要来自规则数量，不值得为了缩短文件而盲目拆碎或合并。
- `game-storage`、`game-records`、`game-settlement` 虽然短，分别负责持久化、快照与最终顺位结算，边界明确。
- `.js` 中只有一行的页面入口承担原生 Page 注册，配套 definition 用于组件复用，并非无意义文件。
- SVG 和 PNG 牌面、旧记录版本兼容、独立计算器页面均有实际引用或测试用途；本次没有按文件大小或新旧名称直接删除。
