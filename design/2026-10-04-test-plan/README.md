## 自动化方案与边界

比较六种可行方向：只补 Node 回归最快但无法验证 WXML；只做界面录制易受布局变化影响；仅做截图无法证明分数正确；迁移到大型 Web 测试框架不适配原生小程序且成本高；直接建设真机设备池投入较大；保留 Node 并增加开发者工具测试最符合现有结构。建议采用最后一种，设备验证作为单独扩展层。

| 层级 | 方式 | 验证内容 | 运行条件 |
| --- | --- | --- | --- |
| L0 | 静态检查和资源清单 | 页面注册、组件引用、WXML 事件、资源存在 | Node，无微信依赖 |
| L1 | 现有断言框架和数据驱动测试 | 算法、规则、结算、转换、不变量 | Node，每个套件独立进程 |
| L2 | Page/Component 测试宿主和 wx Mock | 表单、生命周期、持久化、错误回调、定时器 | Node，确定性虚拟环境 |
| L3 | miniprogram-automator 候选驱动 | 真正点选、输入、渲染、页面栈、组件事件 | 已登录并可自动化启动的微信开发者工具，先验证兼容性 |
| L4 | 截图与真实 Canvas 输出比较 | 布局遮挡、牌面、滚动、战报图片 | 固定工具版本、字体、窗口尺寸和测试数据 |
| L5 | 独立真机任务 | 系统相册权限、实际落盘、原生分享和反馈 | 专用测试机与账号，设备驱动可用性另行验证 |

微信小程序组织的 [mpflow E2E 文档](https://wechat-miniprogram.github.io/mpflow/docs/plugin/e2e-test.html)说明使用 miniprogram-automator 操作开发者工具。这里仅据此选作技术验证候选，不要求项目采用 mpflow。微信[自动化快速开始](https://developers.weixin.qq.com/miniprogram/dev/devtools/auto/quick-start.html)本次无法抓取，具体接口、工具版本及组件访问能力需要在实施第 1 阶段验证并锁定，不能承诺任意版本即装即用。

全自动验收定义：完成一次环境配置后，L0 至 L4 应能单条命令运行，无人工点选，失败返回非零状态，自动保留证据。L5 未接通前报告必须写“平台真机验证未执行”，不可算作全链路通过。反馈提交和好友发送只测入口及参数，常规自动回归不向真实他人发送消息或后台制造反馈。
